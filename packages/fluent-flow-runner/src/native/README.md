# Native transports

[Runner](../../README.md) · [Unit tests](../../tests/unit/native/README.md) · [Native probes](../../tests/native/README.md)

These modules let the runner talk to Claude Code and Codex directly, with no Paseo in between. They hold no policy and choose no model, mode or backend. The adapters (later tasks) decide those.

| File | Purpose |
| --- | --- |
| `jsonl.js` | `createJsonlChannel({ readable, writable, maxLineBytes })` frames newline-delimited JSON over a child's stdout/stdin. It fails closed: a line over `maxLineBytes` (default 8 MiB), invalid JSON or a torn final line ends the channel with a `NativeProtocolError` and no later line is parsed. `send` waits for the write callback and `drain`, and rejects with `stream_closed` once the channel is closed. `closed` always resolves (never rejects) to `{ error }`. `fail(error)` lets an adapter end the channel: the first error wins, both streams are destroyed and later sends reject. |
| `claude-control.js` | `createClaudeControl(channel, { onControlRequest, onCancelRequest })` speaks the Claude Code stream-json control protocol. Outbound `control_request`s are correlated by `request_id` and time out with `control_timeout` (late answers are dropped). Each CLI `control_request` is answered at most once, a handler throw becomes an error response, and `control_cancel_request` drops the late answer. `sendUser` writes `client_composed: true` so the CLI delivers text as written. The CLI's echo of our own answers is ignored. Any other unknown response fails pending and later requests and closes the channel (`channel.fail`) with `unknown_response`. |
| `codex-rpc.js` | `createCodexRpc(channel, { onServerRequest, onNotification })` speaks the Codex app-server protocol: JSON-RPC shapes without a `jsonrpc` member. Server requests are answered under the same id, notifications dispatch in order, and a response for an unknown id fails pending and later requests and closes the channel (`channel.fail`) with `unknown_response`. |
| `native-env.js` | `buildNativeEnv({ backend, contextDir, parentEnv, reportingToken })` is the only source of a native child environment. It copies `INHERITED_ENV_KEYS` from `parentEnv` (so `HOME` is inherited unchanged) and adds the fixed backend keys. Codex also gets `FF_QUESTIONS_TOKEN` when `questionsToken` is given. Claude gets `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=0`, `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. Codex gets `CODEX_HOME` and, when given, `FF_REPORTING_TOKEN`. Ambient keys, gateways, proxies and `NODE_OPTIONS` never pass. |
| `pins.js` | `NATIVE_PINS` (exact versions and enums from the pinned `--help` output and schema; unchanged since Task 1 because Task 2 consumes them), `NATIVE_OBSERVED` (probe-proven behavior, including per-policy reporting and question outcomes from the `POLICY_OUTCOMES` enum `runs`/`asks`/`refused`/`unproven`), `readNativeVersion`, `claudeArgs`, `codexArgs`, `codexLaunchControls` and `codexQuestionServerOverrides`. |
| `question-mcp.js` | FF's question tool for Codex: `startQuestionServer` serves one tool, `ff_questions.ask`, over loopback Streamable HTTP at `/mcp/<sessionId>` (constant-time bearer, 401/403/404/413). A valid call becomes one pending request (stable `requestId` and `fingerprint`), held as an SSE stream with comment heartbeats until it is answered (`answer`, with `answer_on_host` for secret requests answered from the web), declined, withdrawn (`native_aborted` on a real socket or worker close, `expired`, `shutdown`, or `turn_interrupted` via `withdrawTurn({ threadId, turnId, generation })` when FF sees the exact interrupted terminal turn, because Codex 0.162.1 leaves the call open after an interrupt) or the hold ceiling elapses. `record` is an injected, awaited boundary that only ever sees metadata (no answer value or hash). A seen `responseId` never redispatches. `recoverQuestionRecords` rebuilds outcomes after a restart. No tool annotations and no approval override are set. An `onSettled` callback that throws is logged (`settle_callback_failed`) and never replaces an original record failure, skips its log or becomes an unhandled rejection (Task 6). Task 6 fix round 1: an optional synchronous `admit(request)` seam refuses a call (JSON-RPC `-32603` "Question not admitted") before anything is recorded or published. `withdrawTurn({ threadId, turnId, generation, reason })`, `withdraw` and `close` mark a matching answer that is held at its barrier as invalidated at once, without waiting for it. That answer rechecks after its barrier and before any byte: it withdraws the call and records `answer_refused` (`request_unavailable`), so it is positively unwritten while its barrier stays recorded. Once a write is attempted, its outcome stays the answer's own. If the held barrier rejects instead (fix round 2), the answer still completes the withdrawal. The request is settled and no longer pending. When the withdrawal record succeeds, its timers stop and the held call ends. When that secondary withdrawal record fails, the timers still stop and the request settles `reconciling` with no result, but the held socket is left for the native disconnect or server shutdown to tear down. The caller gets the original barrier error, the response is `reconciling` and never replayed, and a failed withdrawal record is logged (`withdrawal_after_barrier_failed`) without replacing that error. A barrier rejection with no withdrawal leaves the request genuinely pending and retryable, as before. |
| `claude-backend.js` | `createClaudeBackend({ privateDir, log, auth })` is the `claude-code` NativeBackend (contract in [`../supervisor/backend-contract.js`](../supervisor/backend-contract.js)). `readiness(profile)` returns `platform_unsupported` off Linux, `not_installed`/`incompatible` from the version, `invalid_config` when the permission mode's C13 outcome is `refused` (protected reason `required_capability_blocked`) or unrecorded/`unproven` (`required_capability_unproven`), and `sign_in_required` unless `auth.readiness` admits `claude auth status`. `open()` writes `privateDir/<sessionId>/{mcp.json,settings.json}` (0700/0600; hooks disabled). The private root and session dir must lie outside the worktree by path component: the worktree itself or any descendant, `..private` included, is refused with `startup_failed` before anything is written, launches with `claudeArgs` plus `auth.args()` and `buildNativeEnv` plus `auth.env()`, and uses the FF session id as the native UUID. Create is `barrier('create_native_session')`, `--session-id`, `initialize`, `bind`. A barrier without bind (`resume: { nativeSessionId, bound: false }`) opens `--resume`: found binds, the C12 not-found exit creates again with the same UUID, anything else is `reconciling`. Before any prompt it reads `initialize` (auth source, permission mode), `get_settings` (model) and `mcp_status` (server status only; the reported config carries the bearer), and `admitClaudeInit` decides: reporter not connected is `startup_failed`, an auth source the policy refuses is `sign_in_required`, another model or a permission mode other than the C13 init value is `profile_unavailable`. A refused worker rejects its first `send` before the barrier. `send` writes the user message with `uuid = commandId` after its barrier; the receipt is the replayed message (or the `cancelled` lifecycle of a queued one). Respond barrier refs hold only `nativeRequestId`, `requestKind`, `fingerprint`, `source` and `operation` (`answer` or `decline`), the Task 4 ledger's typed metadata. After its barrier, `respond` rechecks the same request: one the native withdrew, or a closed channel, settles `request_unavailable` with nothing written, and a withdrawal or close before the write is attempted settles the same way; a write attempted and then failed is `reconciling` and never retried. `can_use_tool` becomes a pending request (fingerprint `sha256` of the canonical request; choices only from the native offer with the Task 9 labels; `AskUserQuestion` ids `q0..qN`, `secret` false). Admission also runs a fresh read-only `claude auth status --json` in the profile's context (cwd: the session's private dir) and requires `auth.readiness` to admit it, because `initialize.account` alone cannot tell a subscription login from a bearer or profile injected through the context's settings; an unreadable status is `sign_in_required`. `interrupt` sends `cancel_queued:true` after its barrier and returns `{ receipt, terminal, settled }`. Its boundary is formed in the same synchronous step as the interrupt write: a prompt whose `send()` is still awaiting its barrier becomes undispatched and is never written (`send()` returns `{ receipt: { uuid, state: 'cancelled', dispatched: false } }`), and a prompt written before it, started or not, is watched. `settled` lists both, in send order: `{ commandId, outcome: 'cancelled', dispatched: false }` for the undispatched ones, and for the watched ones `dispatched: true` with the outcome native evidence gave it: `cancelled` (its `cancelled` lifecycle or the receipt's `cancelled` list) or the terminal of the result naming it (`interrupted`, `completed`, `failed`). `terminal` is the terminal of a result seen after the interrupt, or null when every prompt was cancelled before it ran. A proven idle worker (nothing in flight, no running turn) returns `{ terminal: null, settled: [] }`. Missing evidence within 30 s, or the native stream closing, throws `ClaudeBackendError('reconciling')`; a receipt alone never counts as stopped. `close` stops the worker's own child; descendants belong to containment. |

## Question answers (Claude)

The `AskUserQuestion` input keeps `answers` as one string per question text (C5 schema). A single-select answer is the label itself. A multi-select answer is a JSON array of the selected labels, so a label containing a comma is never split or joined. Free text goes in the native `annotations[question].notes`. 2.1.317 passes both into the tool result unchanged (Task 5 native test). Two questions with the same text cannot be answered apart, so such a request accepts only a decline.

## Error codes

`NativeProtocolError.code` is one of `line_too_long`, `invalid_json`, `torn_final_line`, `stream_closed`, `control_error`, `control_timeout`, `unknown_response` and `version_unreadable`. Messages are for protected logs and never name credentials.

## Pinned argv

- Claude Code `2.1.317`: `-p --input-format stream-json --output-format stream-json --verbose --replay-user-messages --include-partial-messages --model <m> --permission-mode <mode> --permission-prompt-tool stdio --strict-mcp-config --mcp-config <file> --setting-sources user --settings <file> --add-dir <workspaceDir>`, then `--session-id <uuid>` or `--resume <uuid>`. Probe C4 showed `--permission-prompts host` is not needed. Probe C7 showed that with `--setting-sources user`, the workspace `CLAUDE.md` loads only from an `--add-dir` directory, and only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. Project settings and hooks stay off. See the [evidence README](../../tests/native/evidence/README.md).
- Codex `0.162.1`: `app-server --listen stdio:// --strict-config`, then `-c key=<TOML value>` per override. The probe's overrides all pass strict config (X2). Every launch must include `codexLaunchControls()` (`features.plugins=false`, `features.apps=false`); without them 0.162.1 contacts github.com and chatgpt.com (X12). The production adapter must merge them into its overrides.
- Project config route (Codex 0.162.1): sending `cwd` in `thread/start` writes `trust_level = "trusted"` for the project and starts the servers in its `.codex/config.toml`. X4b is the passing trap record of that behavior. FF never sends it: the worker is spawned with its cwd set to the worktree realpath, `config/read { includeLayers: true }` goes through `assessCodexLayers`, and `thread/start`/`thread/resume` go without `cwd`. X4c and X4e prove that on this route the project layer is reported disabled and inert: no project server starts and no trust is written. X4d proves a trusted (enabled) project layer is refused before any thread starts.

## Codex frozen model and recovery limits (Task 6)

- **Frozen model.** After admission, only a `model/rerouted` for this worker's thread whose valid `fromModel` and `toModel` both equal `profile.model` changes nothing. A different destination, a return from another model to the selected one (Task 7: the destination proves the current model, not that earlier work honored the frozen profile), a missing or invalid `fromModel`, a report for another thread, or a malformed report (missing or non-string `toModel`) emits one `state` event `{ state: 'profile_violation', errorCode: 'profile_unavailable', threadId, turnId, selectedModel, actualModel, fromModel, reason }`; `actualModel` is the reported destination for this thread and `null` when the report proves nothing, and `fromModel` is the valid reported source for this thread or `null`. It fences every later `send`/steer with `profile_unavailable`, including one whose barrier was still pending, and runs the supervisor-bound `stopOwned` once (shared with the unexpected-MCP stop; a throw or `uncertain` result makes the session `reconciling`). Usage keeps aggregate tokens with per-turn `modelAttribution` (`mixed` for the rerouted turn, `unknown` when the evidence proves nothing), never all tokens under the new model. A native terminal that arrives afterwards is emitted as `terminal: 'failed'` with `nativeState` (the native status) and `errorCode: 'profile_unavailable'`. There is no retry, fallback, model override or policy change.
- **Bound but unadmitted recovery.** A lost `thread/start` response may bind the exact native thread found by `thread/loaded/list` and `thread/read`, but on 0.162.1 its settings cannot be read (the turnless rejoin finds no rollout), so open stays `reconciling` with zero prompts and no second `thread/start`. Task 11 must resolve this case durably, with no blind recreate or replay and no false success. A normal cold create is unaffected.
- **Model diagnostics.** Only a 400 reported as `other` whose verbatim body has `error.code === 'model_not_found'` is `profile_unavailable`. A 404 is a generic `failed`: 0.162.1 drops the provider code (X15).
