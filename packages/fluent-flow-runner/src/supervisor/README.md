# Supervisor core

[Runner](../../README.md) · [Unit tests](../../tests/unit/supervisor/README.md) · [Containment tests](../../tests/native/containment/README.md) · [Connector](../connector/README.md) · [Native transports](../native/README.md)

The supervisor is a host-local process, separate from the polling connector, that owns native workers for the standalone backends. This directory holds its core: exclusive ownership, the durable ledger, owner-only IPC, cgroup containment and (Task 7) native dispatch of the composed `claude-code` and `codex` backends. Refusal details (`containment_unavailable`, `backend_not_composed`, `profile_revision_mismatch`, `not_ready`, `worktree_conflict`, `recovery_required`, …) go only to the host log; replies carry a public code.

## Native dispatch (Task 7)

The connector's executor sends v2 native commands over IPC; the supervisor resolves everything else itself. `submit` carries the command identity, the frozen `profileId`/`profileRevision`, a repository key (never a path), the run branch and base ref, the session reporting URL and credential (used for the native, never written to the ledger), prompt text, or a permission's `nativeRequestId` and response. The supervisor's own profiles and repositories come from its config file.

- **Launch, create_session, summarize (bind stage).** Earlier-lifetime safety first (below), then admission: verified containment and a composed backend (`profile_unavailable` otherwise), the exact local profile whose current revision equals the frozen one (`execution_settings_changed`), the backend's fresh `readiness` (`sign_in_required`, or `profile_unavailable` for any other non-ready state) and a reporting credential (`startup_failed`). A launch then creates the run worktree (`worktrees.js` in the connector directory: `create_worktree` barrier, `git worktree add`, receipt). An additional session uses the run's bound worktree, dirty or not. A worktree conflict is `startup_failed` with nothing modified, except under an existing unresolved `create_worktree` barrier for the run (for example the recorded worktree is now missing or dirty): that is `reconciling`, with no second `git worktree add`, no receipt and nothing modified. The worker opens with the next generation, `openEffects`, a contained spawn (worker intent fsynced before the spawn, identity after enrollment) and the bound owned stop. The outcome is `accepted` with `{ workspaceRef, nativeSessionId, generation }`.
- **deliver** (the initial prompt of a bound command) and **prompt** (follow-ups; `steer`, or `interrupt` then a new turn) go to this lifetime's worker that owns the exact session and backend, through a per-call `prompt` barrier. A follow-up prompt rechecks the profile revision; a control never does.
- **permission** goes through a per-call `respond` barrier; **cancel** through a per-call `interrupt` barrier. Neither looks up a profile, so a withdrawn or unready profile does not block them. A control for another backend than the session's is `execution_settings_changed`.
- A session no worker of this lifetime owns stays `reconciling` until an authorized explicit Cancel or new prompt follows the lifecycle rules below. It is never reopened automatically.
- An effect that threw after its barrier is `reconciling` whatever its public code (for example Codex `request_unavailable` with `no_active_turn` before the RPC, or `steer_not_submitted` after the native refused a written `turn/steer`): no `no_write` is inferred from a code, no receipt is forged and the barrier stays. Before its barrier it is `failed` with the backend's public code. A respond `request_unavailable` after its barrier is recorded as `no_write` because both backends return it only from a recheck before the write is attempted (`claude-backend.js` respond, `codex-backend.js` `respondApproval`, and the question server's withdrawn answer).
- Replays: a command with an outcome returns it (with the binding for launch-like commands). A command accepted but never barriered runs now. Anything barriered without an outcome is `reconciling`.

**Bound owned stop.** Each worker gets `stopOwned({ reason })` bound to its exact session, generation and recorded leaf. At use it rechecks the recorded worker, the boot id and the leaf (`ops.leaf`), kills only that leaf and returns `quiesced` only when the leaf reads empty within the stop timeout (10 s); anything else is `uncertain`. It runs once per worker: later causes share the result. Its result is recorded as `worker_exit` evidence (`kind: 'owned_stop'`), and a quiesced stop spools a `failed` state (`profile_unavailable` for `model_rerouted`, otherwise `startup_failed`). A child exit is recorded as evidence only, never as an empty cgroup. Fence: from a spooled `profile_violation` or the start of the owned stop until it returns `quiesced`, every native terminal of that generation is spooled with `ownedStop: 'pending' | 'uncertain'`, which projects `reconciling` (with the native terminal kept); only the quiesced stop's `failed` releases it.

**Positive no-write evidence.** When a backend reports that FF suppressed a barriered effect before writing (`receipt.dispatched: false` for a prompt suppressed by an interrupt boundary, a settled entry with `dispatched: false`, a withdrawn answer returned as `request_unavailable`, or an idle interrupt), the supervisor records `no_write { commandId, effect, generation, sessionId, backend, evidence: 'ff_suppressed' }`. It is never a receipt: `classify()` keeps the effect `uncertain`, and Task 11 resolves that exact barrier from this record. Lost evidence stays uncertain.

**Startup admission gate.** After recovery (below), a worker recorded by an earlier supervisor lifetime whose leaf is not proven empty, or an earlier command with an uncertain effect and no `failed`/`applied` outcome (or a `reconciling` outcome) and no operator closure, refuses every new admission with `startup_failed` (protected reason `recovery_required`). An acquired lock, a missing in-memory worker or a child exit never counts as quiescence. A fresh instance admits normally. An operator closure releases the gate for the closed commands.

## Lifecycle and recovery (Task 11)

The IPC server assigns a monotonically increasing epoch to each authenticated
connector attachment. Attachment clears prior control-plane freshness; only a
matching connector can refresh or clear it, and a matching disconnect clears
it without stopping already admitted workers or releasing held poll grants.
Authenticated API successes refresh a 60-second local window. API failures
publish offline before retry or fatal handling.
An undispatched launch, additional session or summary stays deferred while this
window is offline or stale and can be retried after a fresh matching attachment.
Already admitted workers and their controls continue under the durable ledger.

**Recovery on start.** `startSupervisor` runs `recoverOnStart` after the ledger opens and before IPC listens. Per recorded worker: containment unavailable, another boot id (`boot_changed`), a leaf `workerLeaf` cannot prove (`not_owned_leaf`), a missing leaf whose recorded process is still alive, or an unknown `populated` is `reconciling` with no write and no signal. A provable leaf that reads empty is `empty`; a populated one is stopped with `stopContained` and is `quiesced` or `reconciling`. Each non-empty result is recorded as `worker_exit { kind: 'recovery_stop', stop, reason, bootId }`. Commands: an uncertain effect with exact FF no-write evidence (`no_write` whose generation, session and backend match the barrier) gets `resolution { kind: 'ff_no_write' }` (classify then says `resolved`; no receipt is written) and, without an outcome, `failed`/`request_unavailable`. Any effect still uncertain, a bound launch whose first prompt was never written, or a `reconciling` outcome makes the command `reconciling`. A touched session (a worker not found empty, a reconciling command, or an empty worker whose last prompt has no later terminal) gets one spooled `state: reconciling` event `ff:recovery:<generation>`. Nothing is respawned, reopened or replayed. A failed ledger write stops admission (`startup_failed`), leaves the files as they are, and is reported as `admission: 'stopped'`.

**Worker death.** A child exit of a live worker that FF did not stop or close removes it from this lifetime (its pending requests are gone), marks a bound launch whose first prompt was never written `reconciling`, and runs its bound owned stop (`worker_lost`), which spools `state: reconciling` (`ff:worker_lost:<generation>`, with the stop result). An answer naming that generation is `request_unavailable` before any barrier.

**Explicit continuation.** A new `prompt` can close the lost generation and reopen the exact bound native session at the next generation, without a preceding Cancel. It must first satisfy the profile, readiness, reporting, worktree and ownership checks described below, positively quiesce the recorded workers and durably close earlier open commands. Only the new prompt is written; earlier prompts are not replayed. A bound Claude 2.1.317 session killed during its first turn may return `resume_not_found`; that stays `reconciling`. An unbound uncertain Claude create has the separate exact-UUID recreation path below.

**Operator closure.** A `cancel` for a session no worker of this lifetime owns is an explicit closure. It refuses while another command of the session is in flight, while a recorded worker uses another backend, while containment is unavailable, or while an uncertain `create_native_session` barrier has no recorded worker of its generation (nothing proves what was created). Every recorded worker of the session must then be proven quiescent (empty leaf, or `stopContained` of the exact owned leaf of the current boot); otherwise the Cancel is `reconciling` and nothing is closed. On proof, each open command of this exact session and run gets `closure { by, generation, sessionId, backend, stop: 'quiesced', evidence: { nativeSessionId, promptBarrier, promptReceipt } }` and each of its uncertain effects `resolution { kind: 'operator_closed', by }`. Barriers, binds, receipts, worktree and history stay; nothing is opened, resumed, prompted or receipted. One `state: cancelled` event (`ff:closure:<cancelId>`, `closure: 'operator'`) is spooled, slots are settled at once (a Cancel itself never holds a slot), and the Cancel's outcome is `applied` with `closure: 'operator'`. A replay of a closed command returns `failed`/`request_unavailable`; a replay of the Cancel returns its closure, also after a restart. This is the path for the Codex 0.162.1 bound-but-unadmitted create (a lost `thread/start` reply bound from loaded-list/read evidence, a failed turnless rejoin, zero prompts): the closure is not a receipt that the native created, completed or cancelled anything.

**Continuation that closes the lost generation (concern pass, C5).** An explicit prompt for a session with no live worker now itself plays the closure role: it refuses while any command of the session is in flight, while backends differ, while containment is unavailable or an uncertain native create has no recorded worker; it checks the profile revision, readiness, reporting credential and run worktree; it quiesces every recorded worker of the session (`stopContained`, recorded as `worker_exit { kind: 'continuation_stop' }`); and only then closes every other open command of the exact session with `closure` and `operator_closed` resolutions naming the prompt, before it opens the next generation. A reopened worker, and a live worker whose `idle()` is true, always start a new turn: a `steer` is a native steer only into an active turn. A successful reopen spools `binding { nativeSessionId, generation }` (`ff:binding:<generation>`) before the prompt's barrier; the connector maps it to the existing `session_bound` observation, so the server's binding generation is current before any later event of that worker, including its loss. A lost worker's backend is closed after its owned stop starts.

**Exact Claude recreation (C1).** When the session has no bind but exactly one earlier launch-like command with an uncertain `create_native_session` barrier whose `ref.uuid` is the session id, the continuation resumes `{ nativeSessionId: uuid, bound: false }`. `open({ effects })` then carries `prior`; the Claude backend, on the native's own `No conversation found with session ID` exit, calls `effects.absent({ nativeSessionId, evidence: 'resume_not_found' })` before its create barrier. Only that exact UUID is accepted (once); the supervisor writes `resolution { kind: 'native_absent', by: <prompt>, evidence: { nativeSessionId, source: 'claude_resume_not_found', generation } }` and the original command's `closure`, and only then the backend writes the prompt's own `create_native_session` barrier, spawns `--session-id <uuid>` and binds the new generation. If resume finds the session and binds it, the original create gets `native_present` instead. Anything else (a refused absence, no exact bind, a worker not proven quiescent) leaves the original create uncertain and the prompt `reconciling`. Resolution evidence is typed per kind (`ff_no_write`, `operator_closed`, `native_absent`, `native_present`); extra, missing or mistyped fields are refused. A generation's spawn may run a second time only after its first process exited (`child_exit`) and its leaf reads empty; the new identity replaces the old one on the same intent.

**Archive without its receipt (C2).** `wrapupArchive` writes `archive_attempt { runId, workspaceRef, branch }` immediately before `git worktree remove`. A later preflight of a run whose recorded worktree is missing and whose attempt has no receipt adds `archive_receipt_missing`. An explicit `wrapupArchive` then closes the attempt only when every other blocker is clear (quiescent, nothing unresolved), the directory is gone and Git no longer lists the worktree: it records `archive_resolution { outcome: 'unknown', evidence: { directoryMissing: true, worktreeRegistered: false, branchHead } }` and answers `archive_outcome_unknown`. It never writes `worktree_archived`, never recreates or deletes anything, and keeps the branch. Later preflights, archives and restarts return the same blocker; the run's workspace is gone (`workspace` returns null, new work is refused). Without an attempt record, or with other blockers, a missing worktree stays `worktree_missing`.

**Stop.** `stop { scope: 'all', timeoutMs }` stops admission, interrupts every active turn under its own accepted `stop_interrupt` command (barrier and receipt, plus the `ff:cancel` confirmation), closes each live worker and stops it with `stopContained` (grace up to half the timeout), then kills any other proven populated leaf. `stopped` only when every recorded worker is proven empty and no observed descendant escaped; then the supervisor exits. Otherwise `uncertain` and the supervisor keeps running so `status` can show it.

**Escapes.** Every process seen in a worker leaf (status, slot settlement, wrap-up) is remembered with its start time and boot id. `detectEscapes` reports one still alive (same start time and boot) whose cgroup is now outside the `ff-*` scope as `descendants_escaped`. It makes the session `reconciling` (`ff:escape:<generation>`), blocks wrap-up (`descendants_escaped`), keeps the slot, makes `stop` `uncertain` and shows the worker as `escaped` in `status`. Same-uid escape remains a limitation: a process never seen in the leaf, or one that escaped before any observation, is not detected.

**Status.** `status` adds `supervisor.pid`, `capacity` (`{ limit, used }` per backend) and, per worker, `state` and `startedAt` (the intent time). It carries no payload.

**Events.** Every native event passes `spool-privacy.js` and is spooled as `{ backend, event, terminal?, receiptFor? }`. A native `interrupted` terminal carries no cancellation. A Cancel is confirmed only from its own interrupt call's positive evidence (the `interrupted` terminal that call waited for, or a proven-idle worker / never-written prompts): the supervisor spools `ff:cancel:<commandId>` `{ state: 'cancelled', cancelCommandId, generation, nativeTerminal, dispatched, settled }` from the call's result, so neither pump timing nor a later prompt can change it. A turn that ended on its own (`completed`, `failed`) keeps its actual status and gets no confirmation. `events` replies hold whole events up to 768 KiB. An event larger than 512 KiB is announced alone (`payload: null, chunked: { bytes }`) and read with `eventChunk { seq, offset }` in base64 slices of 384 KiB of its exact UTF-8 JSON. `client.js` `fetchEvents` rebuilds it and throws `event_incomplete` on a short, oversized or undecodable result, so an incomplete event is never returned or acknowledged. The frame limit (1 MiB) and every other bound are unchanged.

**Containment operations.** Dispatch uses `ops` (`leafPath`, `createWorker`, `spawn`, `leaf`, `read`, `kill`). Production derives them from the verified scope (`createWorkerCgroup`, `spawnContained`, `workerLeaf`, `readContainment`, `killContainment`); a test containment passes its own as a constructor argument.

## Dispatch evidence

Every native effect gets its own fsynced barrier immediately before it happens: `create_worktree`, `create_native_session`, `prompt`, `respond` and `interrupt`. A barrier is never written twice for the same command and effect. After a restart, `classify(commandId)` returns `undispatched` when there is no barrier. Otherwise each effect is `receipted` (a receipt exists, or for `create_native_session` a binding for that session and generation) or `uncertain`. Uncertain effects follow their recovery rule (Tasks 5 to 7) and are never replayed. Event kinds add `binding` (Task 11). A barrier `ref` is a plain object that may not restate `commandId`, `effect` or `generation`. A `respond` ref accepts only typed request metadata: `nativeRequestId` and `source` (`web` or `local`) are required, and `responseId`, `requestKind` (`permission` or `question`), `fingerprint` (the 64-hex native request fingerprint, never an answer hash) and `operation` (`answer` or `decline`) are optional. Answer values, hashes and any other field are refused.

`open({ effects })` effects are bound to the opening command and generation. They barrier only `create_native_session` and bind once, so a later prompt, answer or interrupt can never be recorded under the launch command.

Prompt, respond and interrupt barriers are per call. `NativeWorker.send/respond/interrupt` take a mandatory `barrier` argument built by `createCommandBarrier({ ledger, commandId, effect, generation })`, bound to that call's exact command, effect and worker generation. It is single-use: any second call, including after a failure, rejects without writing. The backend awaits it immediately before its single native write, rejects a call without one, and writes nothing when validation or the barrier fails. The supervisor writes no other barrier for these effects. Codex question answers reuse it: question-mcp's `answer_barrier` record is mapped by `answerBarrierRef()` (`requestId` becomes `nativeRequestId`; generation stays bound by the barrier) and written through that same barrier at the same pre-write point. Host-local answers take the same path with `source: 'local'`.

A failed durable write (ENOSPC, EIO, fsync) sets `admissionStopped` and refuses every later write. The file is left as it is. Corruption, an unknown record type or any version other than 1 fails closed with the file preserved. Versions and references are checked before a torn tail is truncated, so a rejected ledger keeps its exact bytes even when its last line is torn. `ledger.jsonl` is opened only through `private-file.js`: a symlink, a non-regular file, a foreign owner or a mode other than 0600 fails with `supervisor_file_unsafe` before any read, truncate, append or chmod. The connector journal keeps its own path-based rules.

Worker intent (with its cgroup path) is fsynced before a spawn. An intent with neither identity nor exit is reported with `needsRecovery: true`.

`status` reports each worker's `populated` as `true`, `false` or `null`. `null` means unknown: containment is unavailable, the recorded path cannot be proven to be this supervisor's worker leaf, or the leaf is gone while the recorded process is still alive. Unknown work is never reported as empty, and `needsRecovery` is then `true`. It is also `true` for a populated leaf whose identity is from an earlier boot. `stop` stops admission and writes `cgroup.kill` only for a leaf proven by `workerLeaf`, meaning the exact `<scopePath>/w-<generation>-<sessionId>` of the recorded worker, inside this supervisor's verified `ff-*` scope, not a symlink and owned by the uid. Its recorded identity, if there is one, must be from the current boot. An intent without identity is killed only through that same exact-leaf proof. `stop` returns `stopped` only when every recorded worker is proven empty. Anything unknown or unprovable is `uncertain` and gets no write or signal. Tasks 7, 8 and 11 treat `populated: null` and `uncertain` as unresolved, never as quiescent. `startSupervisor().close()` closes this lifetime's workers' direct children; their containment stays authoritative, and graceful stop/recovery is Task 11.

Events are spooled with contiguous sequence numbers before the connector can read them. They are idempotent per session, generation and native event id. `events { afterSeq, limit ≤ 500 }` reads, `ackEvents { uptoSeq }` moves the durable cursor forward and `hello` returns it, so a reconnecting connector resumes from the last acknowledged event. Unacknowledged events are delivered again.

## IPC

The socket is `<stateDir>/supervisor/ipc.sock` when it fits 107 bytes. Otherwise it is `$XDG_RUNTIME_DIR/fluent-flow/<first 16 hex of sha256(realpath(stateDir))>/ipc.sock`. Every directory must be a 0700, uid-owned, non-symlink directory or the call fails with `SupervisorUnavailable`, and the socket itself is 0600. The handshake is client nonce, then server proof `HMAC-SHA256(secret, 'server|' + clientNonce + '|' + serverNonce + '|' + instanceId)`, then client proof with `client|`. The client sends nothing after `hello` until the server's proof checks out. The 32-byte secret (`ipc-secret`, 0600) never crosses the socket.

Transport bounds: every frame in either direction, complete or partial, is measured in bytes before it is parsed and may be at most 1 MiB (`MAX_FRAME_BYTES`). A longer frame, invalid UTF-8 or malformed JSON drops the connection. A reply that would be larger is replaced by error `response_too_large`, and a request that would be larger is rejected by the client with `request_too_large`. Each connection may have at most 64 requests running or queued (`MAX_PENDING_REQUESTS`). More get error `overloaded` at once and are not queued. A peer that leaves more than 8 MiB of replies unread (`MAX_OUTBOUND_BYTES`) is disconnected. After the handshake each request is `{ id, method, params? }`, where `id` is a positive safe integer (as `client.js` sends), `method` is a string of at most 64 characters and `params`, if present, is a plain object. Any other envelope closes the connection before admission, so no handler runs and no id is reflected. A reply that still cannot be framed drops only that connection and never escapes the socket callback. None of this acknowledges anything: events stay unacknowledged until `ackEvents`. A request refused explicitly before admission or queuing (an invalid envelope, `overloaded`, `forbidden`, `request_too_large`) runs no handler and has no effect. A dropped connection or a missing reply after a request was admitted has an unknown outcome until the ledger reconciles it (`classify`); the client never replays it blindly, and the connector acks it `ambiguous`. `events` replies stay under the frame limit by byte-bounding whole events and chunking a large one (see Native dispatch).

Only one `connector` client may be attached at a time; `cli` clients may connect alongside it. Methods: `hello`, `submit`, `deliver`, `events`, `eventChunk`, `ackEvents`, `controlPlaneStatus`, `status`, `stop`, `pendingQuestions`, `localAnswer`, `workspace`, `wrapupPreflight`, `wrapupCloseSessions` and `wrapupArchive`. Each is limited to a role. `controlPlaneStatus` is connector-only and carries the authenticated connection epoch, so a queued request from an older connection cannot restore freshness after a replacement attaches. Error replies carry only a code; details go to the host log. `pendingQuestions` lists this lifetime's workers' pending requests for the host operator (FF `requestId`, session, generation, fingerprint, `hostOnly`, and the questions as asked; never an answer). `localAnswer` (`cli` role only) is the host-local answer path below.

## Answers (Task 9)

A request's FF `requestId` is the first 32 hex of `sha256(sessionId|backend|generation|nativeRequestId)`; the server lists it and `pendingQuestions` shows the same id. Web answers (`submit` kind `permission`) name the request's `generation` and `fingerprint`: another generation is `request_unavailable` before any barrier, and the fingerprint is passed to the backend, which refuses a mismatch. Web and host-local answers to one request (session, generation, native id) run one at a time through the supervisor, so a race gives one native response; the backend (or the question server) refuses the next with `request_unavailable`. `answer_on_host` and `invalid_response` from the question server are returned unchanged. Web selections that name options by `optionIds` (fix 1) are resolved, inside the serialized answer section immediately before dispatch, against this worker's exact live request (same native id and fingerprint, after the generation check) into the original labels the backend validates; unknown, repeated, out-of-range or cross-question ids and mixed id/label entries are `invalid_response`, a request no longer live or another fingerprint is `request_unavailable`, and nothing is written. Selections with `selected` labels keep the direct contract. A replayed local id with a barrier but no outcome (with or without a receipt) stays `reconciling` and is never dispatched again or marked failed.

`localAnswer { localCommandId, requestId, selections }` answers one pending question. The ledger keeps only `accept` (`kind: 'local_answer'`, `digest: 'local'`, `requestId`, `fingerprint`, `generation`, `operation`, plus run, session and backend), the respond barrier (typed metadata, `source: 'local'`), its receipt or no-write evidence, and the outcome state. The selections exist only in that call: no value, hash or digest of one is written anywhere. The typed text and every chosen label (secret or not) are registered with `spool-privacy.js` before the answer is dispatched, so a later native echo is spooled as `[local answer]`; events already spooled (the question and its options as asked) are not rewritten. A dispatched host answer spools `ff:local:<localCommandId>` `{ nativeRequestId, state: 'resolved', resolvedBy: 'host' }`, never the value. A seen `localCommandId` returns its recorded state and never dispatches again, whatever selections come with it; one accepted by an earlier lifetime and never barriered becomes `failed`/`request_unavailable` (its value is gone; answering needs a fresh id). An id refused because nothing was pending stays refused for this lifetime. Nothing answers a request on a disconnect, timeout or browser close: those withdraw or leave it pending. Limits as in `spool-privacy.js`: known exact values only, not DLP, and the native keeps its own history.

A fresh host-local answer is admitted only while a connector is attached and
the control plane is fresh. Otherwise it returns
`failed`/`request_unavailable` without a ledger record or native effect. An
answer already accepted but waiting behind another response rechecks the same
fence immediately before value registration and native dispatch; loss at that
point records a failed outcome without a respond barrier. Replays of an
existing local command id are resolved before this connectivity fence.

## Summaries and wrap-up (Task 8)

**Cursor domain.** Every native observation carries `providerCursor = { epoch: 'ff-native-v1:<backend>', seq: '<ledger seq>' }`. The ledger sequence is 1-based, contiguous and ledger-wide, so it only grows within a session. The server keeps the highest cursor it received per session and freezes it into an explicit summarize command.

**Capacity (Task 10).** Each standalone backend has the owner's cap (`capacity` in the local profiles file, an integer of at least 1, default 1); primary and summary sessions share it. The connector calls `reserveSlots {}` before each poll and gets `{ availableSlots }`, every slot no session and no earlier poll holds (at most 64 per backend per poll), held as in-memory poll grants; after the poll it returns the unused ones with `releaseSlots { unused }`. `reserveSlots { notAfter? }` makes each reservation a batch with its own `grantId` and its poll's server-clock deadline, and replies `{ availableSlots, grantId, heldBatches }`, where `heldBatches` lists earlier batches no command has used (lost or aborted answers, deferred claims, an earlier connector connection). `releaseSlots { grantId, unused, version? }` returns grants of that batch only; with `version` (the batch's version in the snapshot the release was computed from, changed by every use or return of its grants) a changed batch is refused (`{ released: false, stale: true }`), so a stale count can never return a grant a still-claimed command owns (fix round 1, I2). A Cancel's positive no-dispatch result is recorded in its ledger outcome as `dispatched: false` (the only extra outcome field) and returned again on any same-id replay, also after a restart (fix round 1, I3). A `slotGranted` submit carries its poll's `grantId` and uses that batch (else the oldest batch with a grant); a `slotHeld` redelivery uses the oldest. An admitted submit turns its grant into the session's reservation before any effect, so a connector that reconnects while it is still running sees no grant to return for it (concern pass 2, real-IPC test). Batches are never returned on elapsed time or a connection close. A slot-requiring command (`launch`, `create_session`, `summarize`, or a `prompt` to a session not holding a slot) reserves its session's slot after every refusal check and immediately before its first effect: from a grant when the server delivered it with `slotGranted`, otherwise only from a slot no grant covers. With none free the reply is `{ state: 'deferred' }` and nothing beyond the acceptance is recorded, so the same command id is admitted on redelivery. A reservation is never above the cap. A session keeps its slot while `holdsSlot` is true for what a fresh observation shows: an in-flight or unsettled (reconciling, uncertain) command, a bound launch whose first prompt is not delivered, an active turn, a pending request, any process in the worker's leaf other than the worker itself, an escaped worker, or anything unreadable (unverified containment, an unreadable leaf, an earlier lifetime's worker not proven empty). Settlement is observed on every `reserveSlots` and before a deferral; an idle retained worker alone frees its slot without being stopped (Task 8 archive still treats any live worker as owned activity). A lowered cap stops new admission and never releases or stops a session. The rule is strict: the worker process alone is the configured executable's process, with no allowance for helper or launcher children. A worker started through a launcher that keeps the real binary as its child (the npm `codex` launcher) therefore keeps its slot until it is positively closed; a profile that names the pinned platform binary directly is the supported path for idle release (see the [runner README](../../README.md)). FF never substitutes the executable. A claimed `cancel` for a session whose launch this supervisor never saw (and no worker) is recorded as a durable fence: a later delivery of that launch is refused before any effect (`request_unavailable`), across restarts. A cancel for a launch accepted here whose recorded effects stop before anything native (none, or only its receipted worktree, which stays) settles that launch as never started (`request_unavailable`) and replies `{ state: 'applied', dispatched: false }`; after a native-create or prompt barrier without its proof the outcome stays the effect's own (`reconciling`), never a guessed no-effect; for a bound launch whose first prompt was never written, the launch is settled the same way before the interrupt, so that prompt is never written.

**Summary source and prompt (Task 8, concern C1).** A `summarize` submit carries `summarySource: { sessionId, sourceCursor: { epoch, seq } }`. Before any effect, `summarySourceText` (summary.js) must read the source session's complete assistant text (Claude `assistant_text`, Codex completed `agentMessage`) from its first event through `seq` inclusive, in spool order, each event whole, with the cursor in the summarizing backend's domain; otherwise the command fails with `summary_unavailable` (protected reason in the host log: missing or non-integer cursor, foreign or other-backend domain, beyond the recorded history, another session's or run's event, unknown session, a history gap, or no assistant text) and no worker is opened. It never falls back to all or latest history. At `deliver` the connector sends only the server's prompt; the supervisor reads the same frozen source from its own ledger again and writes `<server prompt>\n{"history":{"sourceSessionId","sourceCursor","assistantText"}}` as that command's single prompt, under its existing prompt barrier. The history never crosses IPC, so a frozen source larger than one 1 MiB frame is delivered whole; there is no FF size cap on it (an earlier `summarySource` IPC method with a 768 KiB cap was removed).

**Wrap-up.** `wrapupPreflight({ runId, repositoryKey, workspaceRef })` is read-only and returns `{ owned, workspaceRef, directoryKnown, sessions, git, blockers }`. Blocker codes: `ownership_unverified` (no receipted `create_worktree` barrier for the run, a mismatched reference or path, or Git does not show a worktree of the repository on the recorded branch), `worktree_missing`, `descendants_unverifiable` (containment unavailable, a leaf that cannot be proven, a worker needing recovery, or a live recorded process that cannot be located), `owned_activity` (a live worker of this lifetime, idle or not, or a populated leaf), `descendants_escaped` (a live recorded worker process outside its own leaf, through the containment `holds` operation), `pending_requests`, `unresolved_commands` (in flight, no outcome, `reconciling`, an uncertain barrier without no-write evidence, or a bound launch-like command whose initial prompt was never delivered), `worktree_in_use` (any other process of this uid whose `/proc/<pid>/cwd` or an open fd lies in the worktree; the scan only ever adds blockers and never proves absence). A same-uid process (or one whose owner cannot be read) whose cwd or fds cannot be read while it still exists is unverifiable and blocks as `descendants_unverifiable` (protected log `native wrap-up process state unreadable`); only a positively gone process (its /proc entry vanished, or a zombie) is skipped, and another uid is excluded only after its owner was read (concern C2). Typical Linux desktops run non-dumpable same-uid processes (systemd --user, ssh-agent, gpg-agent), so on such a host every native archive is blocked by this rule; see the Task 8 report and the Git codes `uncommitted_changes`, `untracked_files`, `no_upstream`, `unpushed_commits`, `git_unreadable`, `upstream_unverified` and `upstream_mismatch`. **Authorized upstream (Task 8 fix 1).** When the run worktree is created, `authorizedUpstream` (worktrees.js) freezes the run branch's push target from the source repository's own Git configuration into the `create_worktree` barrier ref (`upstream: { remote, destination, trackingRef, pushUrlSha256 }`, or `null`), before any native work exists. Remote precedence: `branch.<b>.pushRemote`, `remote.pushDefault`, `branch.<b>.remote`, else the only configured remote; `.`, an unconfigured remote or several remotes with nothing selecting one are no authority. The record is one exact target (fix 2): the destination is `refs/heads/<b>` unless the remote's push refspecs map it elsewhere, and every applicable refspec must map it to the same ref (no match, a negative match or distinct destinations: no authority); the tracking ref is the destination through the remote's fetch refspecs, again exactly one ref; the push identity is the SHA-256 of the exact bytes of the remote's single effective push URL from `git remote get-url --push --all` (fix 3: read as raw bytes, only each record's terminating newline removed, no trimming; more than one distinct URL, including URLs differing only by whitespace, is no authority; byte-identical repeats are one URL; a configured value containing a newline cannot be framed without loss, detected by comparing the record count with the NUL-framed configured values, and is no authority; the URL is never stored or logged). Nothing is fetched, pushed or configured. A null or missing expectation (including every record made before this change) blocks archive as `upstream_unverified` and never prevents a run from starting. Preflight and the final archive check both require `branch.<b>.remote`/`merge` to equal the frozen remote and destination, the remote's current single push URL, push mapping and fetch mapping to resolve to exactly the frozen identity, destination and tracking ref (a later second URL or mapping is `upstream_mismatch`), the tracking ref to exist and HEAD to be no commits ahead of it; anything else is `upstream_mismatch` (for example a local backup branch, another remote or ref, or a changed push URL), `no_upstream` or `unpushed_commits`. `archiveRunWorktree` returns the final sample it validated, and that sample (HEAD and upstream) is the `worktree_archived` receipt and the public result. `wrapupCloseSessions({ runId })` is the explicit closure: it refuses as a whole while any worker has a pending request, is not proven idle (`worker.idle()`), a command is unresolved or containment is unavailable; otherwise each worker is closed and then stopped through its own bound stop (reason `wrapup`, no failed-session event), and only `quiesced` counts. `wrapupArchive` reruns the whole preflight immediately before `archiveRunWorktree` (never `--force`), refuses admission and first-prompt delivery for the run while it runs (cancel and permission answers stay allowed), ends the check with a synchronous recheck of live workers and unresolved commands so an admission that was already in flight (for example on a dropped connector connection) cannot be missed (concern C3), and writes the `worktree_archived` ledger receipt after the removal; a repeated call returns that receipt. A closed session refuses later controls with `request_unavailable`; after archive every new command of the run is refused and `workspace` returns no directory. A crash between the removal and the receipt leaves `worktree_missing`, which blocks and never forces (Task 11 owns that recovery).

## Containment

`probeContainment` reports `verified` only when all of these hold:

- `/proc/self/mountinfo` shows a cgroup2 mount at `cgroupRoot` that no later mount shadows.
- `/proc/self/cgroup` has a single unified `0::` path whose directory and `cgroup.procs` are owned by the uid and writable.
- `mkdir <own>/ff-<instanceHash>` yields `cgroup.procs`, `cgroup.events` and `cgroup.kill`.

Writes stay inside that `ff-*` subtree: worker leaves `w-<generation>-<sessionId>`, `cgroup.procs` enrollment and `cgroup.kill`. `killContainment({ scopePath, cgroupPath, generation, sessionId })` writes only to a leaf `workerLeaf` proves, and opens `cgroup.kill` without following a symlink. A path that merely contains an `ff-*` component is not authority. `readContainment` takes `populated` from the leaf's own `cgroup.events`. A descendant that vanishes during the walk is skipped; only a missing leaf root raises ENOENT. Nothing writes `cgroup.subtree_control`, controller files or any other path, and nothing uses sudo, sysctl or systemd. `spawnContained` runs a `/bin/sh` shim that writes its PID to the leaf's `cgroup.procs`. The shim reports enrollment on a private pipe and waits until the supervisor has read its identity before it execs. Any failure exits 97 without exec. When containment is unavailable, every standalone profile publishes `platform_unsupported`. The Paseo integration is unaffected.

Residual limit: same-uid code inside a worker can still move itself into another cgroup the uid can write, or ask the user's service manager to start work elsewhere. This module cannot prevent that. Task 11 reports escapes it observes, and Task 8's worktree-use check is a second guard. An escape is never reported as success.

`flock(1)` passes its lock descriptor to the command it runs, so the supervisor itself holds the same lock. It also inherits the verified `owner.lock` descriptor on fd 4, which holds no lock itself. Children the supervisor starts with `child_process.spawn` (default stdio, or detached with `stdio: 'ignore'`) do not receive it; a task-owned fixture test checks this. Killing only the flock parent leaves the lock held by the supervisor. When the supervisor dies, flock exits and the lock frees, even if workers it started are still running. A new supervisor can then take the lock while old workers live. It must find and quiesce them from the ledger and their cgroup before it restores anything (Task 11); the lock alone does not fence surviving workers.
