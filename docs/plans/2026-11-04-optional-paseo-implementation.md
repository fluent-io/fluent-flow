# Optional Paseo integration and subscription-native execution: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** ready for execution; revised after plan review and synchronized with Task 1 evidence and the native-gap rulings · 2026-11-04 · [Plans](README.md) | [Design](2026-11-04-optional-paseo-design.md)

**Goal:** Run Fluent Flow tasks through unmodified Claude Code and Codex on the owner's own subscription login, keep every current execution capability, and make Paseo an explicit opt-in integration.

**Architecture:** A new host-local supervisor owns one native worker per FF session (Claude Code over stream-json, Codex app-server over stdio) inside a verified cgroup v2 scope, plus a durable command ledger with per-effect barriers, an event spool and owner-only IPC. The existing connector keeps the server protocol, fencing, observations, Git and artifact policy and the legacy Paseo path, and routes each command by the run's frozen backend. Two new side tables record run and session ownership.

**Tech stack:** Node 22 ESM, Vitest, raw `pg`, zod, Next.js, util-linux `flock`. Native pins: Claude Code 2.1.317, Codex CLI 0.162.1.

**Spec:** [design](2026-11-04-optional-paseo-design.md), behavior approved by the owner on 2026-11-04. The behavior is binding. Protocol flags named there are hypotheses that Tasks 1 and 1b prove or replace with recorded evidence.

## Global constraints

- Approval covers behavior only. It does not authorize native login changes, paid prompts, production access, commits or PRs. Authenticated UAT needs separate owner authorization (Completion gate).
- Compatibility lists are exact: Claude Code `2.1.317`, Codex CLI `0.162.1`. Any other version is `incompatible` until the native suite passes on it and the list is extended.
- No default engine, model or native policy anywhere. No fallback to API billing, another model, harness, backend or integration.
- FF never changes or supplements the owner's selected native policy: no tool-approval override for FF's own MCP servers, no permission, sandbox or approval change, no Codex Plan-mode switch and no under-development feature. A selected policy that cannot run required reporting or questions without alteration makes readiness `invalid_config`, with the protected reason `required_capability_blocked`, or `required_capability_unproven` while no probe has recorded that policy or a probe recorded it as `unproven` (Tasks 1b, 5, 6).
- `@getpaseo/client@0.12.0` becomes an optional peer (`peerDependenciesMeta`) plus a devDependency, loaded by `import()` only when the process starts with `--enable-integration paseo`. `optionalDependencies` is forbidden. Saved Paseo config, profiles or defaults never enable it.
- Native child environments come only from `buildNativeEnv` (Task 1). Ambient API keys, OAuth tokens, gateway/cloud variables, proxies and `NODE_OPTIONS` never pass. FF never reads or copies default Claude/Codex auth files, never logs out, never sets Codex `forced_login_method`.
- Claude workers always get `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=0`. Resume is exact (`--resume <uuid>`, `thread/resume`), never latest, continue or fork.
- At-most-once FF dispatch: every native effect (worktree creation, native session creation, prompt, permission or question response, interrupt) gets its own fsynced barrier immediately before it happens. A barrier without its receipt or binding after a crash follows that effect's recovery rule (Tasks 5 to 7) and is never repeated blindly. Host-local answers persist metadata only: no value, no hash.
- Keep the 25-second server hold, 1-second early-empty poll floor, independent 200-ms observation flush and 15-second heartbeat.
- Data: one forward-only migration `0022_collab_native_execution` creating only `collab_run_execution` and `collab_session_execution`. No ALTER, backfill, constraint, index or foreign key touches an existing table. Existing v1 commands and journals stay legacy Paseo, unchanged.
- Connector `protocolVersion` stays `1`. New-backend eligibility is carried only by `catalog.formatVersion: 2` and per-entry capabilities.
- Capacity is a host-local cap per standalone backend, default 1 for `claude-code` and 1 for `codex`, published read-only. No DB/admin write and no dashboard setting.
- Standalone precondition: Linux with util-linux `flock(1)`, an owner-only IPC directory, `/proc` process identity with boot id, and a verified delegated cgroup v2 scope owned by the execution owner (Task 4). If any is missing, every standalone profile publishes `platform_unsupported`; the Paseo integration is unaffected. This plan does not assume any particular host provides delegation.
- Never use sudo, sysctl, AppArmor changes, systemd, systemctl, systemd-run or any host service, network or cgroup configuration change. Cgroup writes stay inside the supervisor's own `ff-*` subtree of a verified delegated scope. Native test isolation uses only unprivileged user, network and private mount namespaces (a namespace-local sysfs remount, with capabilities dropped before the test command) and fails closed when they are unavailable.
- Test-only seams are constructor parameters: auth policy, spawner, containment and supervisor client. No env var, flag or config value selects them. Production entry points always build the subscription auth policies and real containment, and the production rejection tests stay.
- RED must fail on a behavioral assertion, never on a missing module, binary, CLI flag, fixture connection or database. Add each new module with its exported signatures and inert bodies (empty or unchanged results) before the first run. Inert bodies never survive GREEN. Refactor with tests green.
- Default `npm test` never spawns a native binary. `npm run test:native --workspace=@fluent-flow/runner` runs the native suite inside the namespace launcher (Task 1) with `FF_NATIVE_REQUIRED=1` and fails when a pinned binary (`FF_NATIVE_CLAUDE_BIN`, `FF_NATIVE_CODEX_BIN` or `PATH`) or network isolation is missing. `npm run test:containment --workspace=@fluent-flow/runner` runs the real-kernel containment suite (Tasks 4 and 11) and fails with `containment_unavailable` when no delegated scope is verified. A native file may skip only when its binary is absent, `CI` is unset and `FF_NATIVE_REQUIRED` is not `1`. A version mismatch or missing isolation always fails.
- Native tests run inside the launcher's unprivileged user, network and private mount namespace, whose only network interface is loopback, with task-owned temp roots. Each test builds an explicit `parentEnv` with `HOME` set to a temp home; the spawn env object adds the XDG config, data, cache and state roots under that home and sets `CLAUDE_CONFIG_DIR`/`CODEX_HOME` to temp context directories. Synthetic model and MCP services listen on loopback random ports with dummy credentials, updaters and telemetry are suppressed, and a deny-all proxy is only a secondary signal. Tests never modify installed CLIs, their settings or logins, never let a native read the user's default home state, never export native or `HOME` variables in a shell and never change the parent environment. They prove protocol behavior, never subscription auth.
- Reuse the finished setup: `npm ci` (584 packages) and the shared DB build on Node 22.23.3; baseline root `npm test` 1,149 passed, 3 pre-existing skips, 0 failures; runner typecheck passes. Do not reinstall. Export only the dedicated test databases: `COLLAB_DB_TEST_DATABASE_URL=postgres://ffuser@127.0.0.1:55432/ff_optional_paseo_db_test`, `COLLAB_ROUTES_TEST_DATABASE_URL=postgres://ffuser@127.0.0.1:55432/ff_optional_paseo_routes_test`, `COLLAB_CONNECTOR_TEST_DATABASE_URL=postgres://ffuser@127.0.0.1:55432/ff_connector_optional_paseo_test`.
- After editing `packages/db/src`, run `npm run build --workspace=@fluent-flow/db` before server, runner or dashboard tests.
- Leave changes uncommitted. The orchestrator reviews per-task snapshots because the worktree carries an inherited uncommitted baseline. Never reset, stash or clean, and never touch the user's services (ports 3000/3847), PostgreSQL instance, Paseo daemon or private `.local` state.
- Repository conventions apply: ESM, raw `pg`, zod validation, pino logging, fail fast (each catch rethrows or states why continuing is safe), and a README in every created directory linking its parent and children.

## Review focus

1. The same question answered twice (two tabs, a double click, different idempotency keys): one native response; the second gets `request_unavailable`. Test in Task 9.
2. A second runner or connector started on the same private state: refused before any native effect; never a second supervisor or ledger writer. Test in Task 4.
3. Retrying a run whose worktree path or branch already exists (dirty leftovers, foreign checkout): reused only when FF-owned and clean, otherwise `startup_failed` with nothing removed. Test in Task 7.
4. Task or steering text that looks like a flag, slash command or file mention (`--resume x`, `/login`, `@README.md`): delivered verbatim. Tests in Tasks 5 and 6.
5. A native CLI updated outside FF between runs: readiness `incompatible`, new Starts and follow-ups refused with `profile_unavailable`, running workers untouched. Tests in Tasks 5, 6 and 7.
6. A Codex question whose call the native aborted, FF withdrew or a user already answered: no answer is written, a later answer gets `request_unavailable`, and a declined or withdrawn call never carries an answer. Tests in Tasks 1b and 9.

**Launcher (as built, accepted by the controller):** `netns-launcher.js` re-runs itself through `unshare --user --map-user=<uid> --map-group=<gid> --keep-caps --net --mount`, the caller mapping the namespace amendment prefers. Inside, it runs `ip link set lo up`, mounts a namespace-local sysfs so `/sys/class/net` describes the new namespace, awaits `assertNetworkIsolation()`, writes `ready` on fd 3, drops namespace capabilities with `setpriv` and runs the command with `FF_NATIVE_REQUIRED=1`. An attempt that ends without `ready` falls back once to `--map-root-user`; after `ready` the command's exit code, 86 included, is final and nothing reruns under another UID. The mapping used is logged with its `uid_map`. A missing `unshare`, `ip`, `mount` or `setpriv`, or setup failure under both mappings, prints `network_isolation_unavailable` and exits 1. The mount namespace is private and the sysfs remount stays inside it. It never uses sudo, sysctl or AppArmor changes and never touches host networking or mounts. Every native test file awaits `assertNetworkIsolation()` in `beforeAll` (after the binary skip rule), so a run outside the launcher fails instead of executing a native with host networking.

**Rules (question tool):**
- Transport: `127.0.0.1:0`, path `/mcp/<sessionId>`, Streamable HTTP. `Authorization: Bearer <token>` is compared in constant time (else 401); an `Origin` header gets 403, another path 404 and a body over 1 MiB 413. Methods: `initialize`, `notifications/initialized`, `ping`, `tools/list` (only `ask`, with its input schema and no annotations) and `tools/call` for `ask`; anything else is method-not-found. FF sets no approval mode for this server, so the owner's policy decides whether Codex asks first.
- Arguments (zod): 1 to 3 questions; ids unique and matching `^[a-z][a-z0-9_]{0,63}$`; header 1 to 80 characters; question 1 to 2,000; options null or 1 to 10 with unique labels of 1 to 120 characters; `multiSelect` and `secret` default false; `allowOther` defaults false and is true when options are null. `_meta.threadId` and `_meta.callId` are required (the shape recorded in X11). Invalid input gets JSON-RPC `-32602`, no record and no request.
- Identity: `nativeRequestId` is `_meta.callId`; `requestId` is the first 32 hex of `sha256(sessionId|codex|generation|nativeRequestId)`, as in Task 9; `fingerprint` is the `sha256` of the canonical `{ threadId, callId, arguments }`. One valid call creates exactly one request, and any `secret: true` makes the whole request secret.
- Records: `record(entry)` is awaited before the effect it guards, and no entry carries answer text, other text or any hash of them. `question_pending` (requestId, fingerprint, generation, secret, correlation) precedes `onPending`; `answer_barrier` (responseId, requestId, fingerprint, generation, source, operation) precedes the first response byte; `answer_written` follows a clean end of the stream; `answer_unknown` follows a failed write after the barrier; `answer_refused` carries its error code; `question_withdrawn` carries `native_aborted`, `turn_interrupted`, `expired` or `shutdown`.
- Response: `text/event-stream` with a `:` comment every `heartbeatMs`, then one JSON-RPC result whose single text item is JSON: `{"status":"answered","answers":{"<id>":{"selected":[...],"other":null}}}`, `{"status":"declined"}` or `{"status":"withdrawn"}`. Declined and withdrawn results carry no answers, and FF never writes a value no user gave.
- Answers: a `responseId` already seen in memory or in `recorded` returns its recorded state and writes nothing, whatever selections come with it. Otherwise a request that is not pending fails `request_unavailable`; a secret request answered from any source other than `local` fails `answer_on_host` (a decline is accepted from either source); selections must cover each question id, use only offered labels (unique, at most one without `multiSelect`) and put text in `other` only where `allowOther` holds, else `invalid_response`. Then barrier, write and `dispatched`; a failed write after the barrier is `reconciling` and is never retried. Answers for one request are serialized, so a race gives one `dispatched` and one `request_unavailable`.
- Withdrawal: the native actually closing the HTTP request (socket close or worker exit) is `native_aborted`. On the pin `turn/interrupt` leaves a held call open (X14c), so when the backend observes the terminal `turn/completed` with `interrupted` it calls `withdrawTurn({ threadId, turnId, generation })`. Through the same per-request arbiter as answers, every pending request of the server's own generation whose `correlation.threadId` and `correlation.turnId` equal those values writes `withdrawn` as `turn_interrupted`; an old generation or another thread or turn withdraws nothing, and nothing waits for a native disconnect. A request without that exact correlation is never matched by guesswork: stop and report its actual shape unless the exact `callId` or item-to-turn mapping is proven first. `holdMs` elapsing writes `withdrawn` as `expired`; `withdraw(requestId, 'shutdown')` and `close()` write `withdrawn` as `shutdown`. Each calls `onSettled`, and a later answer gets `request_unavailable` with no answer barrier or value.
- Recovery: `recoverQuestionRecords` maps a barrier with `answer_written` to `dispatched`, a barrier alone to `reconciling`, `answer_refused` to `failed` with its code, and each `question_pending` without a settlement to `expired`. A new generation never re-offers or redispatches them. Logs carry ids and codes only.

Decisions made in this plan, for review:
- Standalone execution needs Linux, `flock(1)`, an owner-only IPC directory and a verified delegated cgroup v2 scope. Without any of them standalone profiles are unavailable on that host. No host, including the current one, is assumed to provide delegation.
- Same-UID code can deliberately leave the worker cgroup through another writable cgroup or the user's service manager. Observed escapes and processes using the worktree block wrap-up; an unobserved deliberate escape remains a documented limit.
- Native tests need unprivileged user and network namespaces; without them `test:native` fails with `network_isolation_unavailable`.
- A lost native creation never creates blindly: Claude recreates only the same FF UUID after a proven not-found, and Codex binds only an unambiguous owned thread, otherwise the command stays reconciling.
- Claude subscription `authMethod` values come from Anthropic's docs and are proven only by authenticated UAT.
- Paseo opt-in is a per-start flag and is never persisted.
- Three new CLI messages, seven readiness labels and two reworded generic startup failures are listed under Global constraints; the approval action labels are in Task 9.
- Codex questions use FF's loopback `ff_questions` tool, because the pinned native question tool is usable only in Plan mode and cannot mark secrets (X7). FF does not claim native Codex question support, and each call still passes the owner's native approval.
- Codex threads never receive `cwd`. A `config/read` layer gate refuses project configuration, trust and foreign MCP servers, and until X4c and X4e pass any reported project layer is refused.
- FF never alters a selected native policy. A policy that cannot run required reporting or questions makes the profile `invalid_config`.
- A failed Task 1 or Task 1b probe stops Tasks 5 and 6 and returns to the orchestrator; no capability is removed.
