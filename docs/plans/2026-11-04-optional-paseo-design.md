## Requirements and proposed approach

The user requires Paseo to be opt-in and both Claude and Codex subscriptions to work from day one. Keep real task/run/session execution, durable recovery, permissions and questions, streaming output, steering, cancellation, reports, artifacts, usage, summaries and safe wrap-up. Keep existing authentication/RBAC, Projects behavior and the recent bounded polling fix.

Propose two direct native adapters: unmodified Claude Code over bidirectional stream-json, and Codex app-server over stdio. A new Fluent Flow supervisor owns their processes and durable command/event evidence. Paseo remains a separately enabled adapter. The approval covers this behavior; the protocol flags and other engineering choices named here remain hypotheses that the implementation plan's probes prove or replace.

The deployment assumption is self-hosted/open-source Fluent Flow on a user-controlled execution host. The execution owner authenticates directly in each native tool. This does not introduce a commercial hosted execution service, shared subscription credentials, token import, or an FF OAuth broker. Anthropic's published conditions permit running unmodified Claude Code with the end user's own login, subject to its product/Commercial Terms conditions. OpenAI's app-server documentation limits its auth path to local/open-source applications and excludes commercial/hosted services. Broader deployment needs a separate authorization review. See [primary sources](#primary-sources).

Approved decisions: explicit owner-authored engine/model/native policy; dedicated native login contexts; existing project-operator access to mapped account quota; cancel-on-intentional-shutdown; host-local secret answering; a configurable active-session cap initially one per backend; explicit Paseo re-opt-in; and holding release until both native backends meet every required capability. Secret handling has a native-persistence limitation described below. Design approval does not authorize authentication changes or quota-consuming UAT.

### Approaches considered

| Approach | Fit and tradeoff |
| --- | --- |
| Direct native Claude Code and Codex adapters, proposed | Meets the named subscription requirement through the tools' own auth. Requires two protocol mappings and a new durable supervisor. Keeps FF task ownership and native permission/session behavior. |
| OMP process/RPC or SDK as the first standalone engine | Technically offers persistent sessions and controls, but OMP's own Claude OAuth/model routing is not the permitted unmodified-Claude-Code path. An API-only OMP configuration fails the subscription requirement. An OMP layer that merely wraps both native tools adds another owner without removing these adapters. Excluded from day one; a future independent adapter needs its own requirement. |
| One-shot legacy CLI runner or API-only agent SDK | One-shot execution lacks the retained interactive/recovery contract. API-key-only SDK auth fails the subscription requirement. Neither is a substitute for this design. |

There is no default engine, model or permission policy. One connector instance and one host supervisor serve the enabled local profile set, which can include both Claude Code and Codex. Each profile states its backend, model and native permission/sandbox/network settings. Startup requires at least one complete profile, not every configured profile to be valid. Task/project defaults or an explicit Start selection choose one eligible profile for that run; they do not restrict the advertised host profile set. Fresh `npm run runner` setup must not discover Paseo or silently choose an executable, model, credential or policy.

## Small backend boundary

Keep one executor and one command/observation protocol. A selected backend supplies local profile discovery/readiness, owned workspace/session creation and lookup, native event/history normalization, prompt/steer delivery, current-request responses, interruption, summary input history and native archive handling. Shared code retains authorization, command identity, evidence, artifacts and Git policy. Backend creation stays a small explicit switch, not a generic plugin framework.

A run snapshot distinguishes:

- Execution backend: `claude-code`, `codex` or `paseo`.
- Harness: actual executable/interface and compatibility version. Paseo can itself run different harnesses.
- Model/provider: exact owner-selected settings and permitted auxiliary models, separate from the backend name.
- Auth expectation: native Claude subscription, native ChatGPT subscription, or the existing opt-in Paseo configuration. Tokens never appear in snapshots.
- Profile revision, permission policy, supported capabilities, reporting configuration identity and host/workspace ownership.

Freeze this snapshot when Start succeeds. Additional sessions and explicit summaries remain on that run's backend; a separately configured summary profile must be frozen at Start and belong to the same backend. Changing defaults affects future runs only. Native model/config changes inconsistent with the snapshot block new admission. Report actual auxiliary model usage where available instead of pretending every native helper uses the primary model.

The host publishes the exact allowlisted profile set with sanitized backend, capabilities and readiness, including truthful unavailable entries. Browser clients do not send executable paths, native session paths, auth locations or arbitrary native configuration. New-format Start requires both the project's mapping allowlist and an exact profile/backend/capability entry in the latest advertised catalog. Remove the current missing-catalog `{ id: profileId, model: null }` snapshot fallback for new-format runs. Existing server-side role checks remain authoritative.

The latest cached catalog remains valid selection evidence while the host is offline, so an eligible Start can queue without an online host. Offline does not mean withdrawn. A newer catalog that removes the profile or its required capability invalidates that selection; never substitute another entry. Before delivery, revalidate current backend enablement and the frozen profile snapshot. If saved defaults or queued selection are no longer available, return a safe settings instruction and preserve the recorded run without native effects. Missing catalog evidence is not an offline fallback.

Keep current project `run.start` authorization and explicit owner/admin host mappings. Authorized project operators using a mapping consume that configured native account's quota; enabling the mapping is the owner's deliberate delegation, without conveying credentials. Do not add an owner-only Start gate. Public client-only members gain neither Start nor filesystem access merely through membership. This preserved authorization behavior is proposed for approval, not a conclusion that every provider seat/account arrangement permits shared operation. The owner must use an account arrangement permitted by the provider within the stated self-hosted/local scope.

## Setup, authentication and package optionality

Runtime configuration contains `profiles[]` and explicit enabled integrations, not one global backend/profile. Proposed `npm run runner -- --profile <id>` is only a convenience for choosing a project default from the advertised set. It does not hide other configured profiles or dedicate the connector to one backend. Use `--enable-integration paseo` for explicit Paseo opt-in; missing standalone tools and saved legacy defaults never enable it. Each complete local profile independently identifies backend, model, native policy and auth context, and readiness remains separate from configuration completeness.

Profiles live in FF-owned local configuration and require an executable reference, selected engine/model, native auth-context reference and explicit native permission/sandbox/network policy. They do not import Paseo profiles, plugins or credentials. Retain saved host identity, enrollment token, connector instance, repository mapping, profile ID and owner instructions. Missing/corrupt recovery state fails closed; it never resets enrollment or recreates a demo repository.

An existing saved Paseo profile or project default does not count as integration opt-in. Preserve it unchanged. A legacy-only startup without any complete enabled profile stops with a safe instruction to use `--enable-integration paseo` or configure standalone profiles. If other complete standalone profiles exist, the connector can serve them while that saved Paseo default remains unavailable; Start must not silently replace it. Do not overwrite defaults or re-enroll. The demo uses its explicitly chosen profile and launches no AI before Start. A demo Start consumes that selected account's quota; the old OMP/Paseo profile remains available only through explicit opt-in.

Propose dedicated native configuration/auth contexts for the standalone tools. This has an onboarding cost: the owner signs in through each native CLI once in that context. An existing default login is not magically reused. FF must not read or copy default Claude/Codex auth files or implement token import. The native binary stores and refreshes its secrets. Native login remains available and the binaries remain unmodified; FF's subscription profile validation does not disable authentication methods in the tool.

Before the first prompt, inspect sanitized native auth metadata under the same effective context. Claude exposes `authMethod` and auth sources; Codex exposes `account/read` with `refreshToken:false` and auth-mode notifications. Do not expose account email, internal paths or provider diagnostics to the browser. A missing login, changed auth method, exhausted allowance or unavailable model stops delivery with a safe error. There is no API-billing, model, harness or Paseo fallback.

Use an explicit child-environment allowlist. Ambient API keys, injected OAuth tokens, gateway/cloud variables or native helpers must not override a subscription profile. Never log out or rewrite native credentials to repair a mismatch. In particular, do not use Codex's forced-login setting on an existing context when it would log the owner out.

Make `@getpaseo/client@0.12.0` an optional peer and retain a dev dependency for integration tests. Load it dynamically only inside the enabled integration. An `optionalDependencies` entry still installs by default and is insufficient. Standalone installation/startup must work without the SDK, Paseo CLI, daemon, credential files or configuration. Explicitly enabling an unavailable integration produces a safe setup error. No new package or directory is required merely to implement this boundary.

## Native protocols and compatibility

Initial compatibility targets are the observed installed versions: Claude Code **2.1.317** and Codex CLI **0.162.1**. These are proposed pins, not tested minimum-version claims. Accept only versions in a validated compatibility range with required capabilities. A later CLI must not silently change auth, queueing or resume behavior.

| Concern | Claude Code | Codex |
| --- | --- | --- |
| Process | Ordinary `-p` with input/output `stream-json`, verbose output and open stdin | Owned `app-server --listen stdio:// --strict-config`; no connection to the user's daemon |
| Control | Initialize/request/response envelopes; `--permission-prompt-tool stdio` (probe C4: `--permission-prompts host` is not needed) | Bidirectional JSON-RPC-shaped JSONL without the `jsonrpc` property; `initialize` then `initialized` |
| Session | FF-generated UUID with `--session-id`; exact `--resume` only | `thread/start` with persistence, then returned thread ID; exact `thread/resume` only. Neither carries `cwd`, and a `config/read` layer gate runs before both |
| Prompt | Stable FF/native message UUID, verbatim `client_composed:true`, replay receipt and result correlation | `turn/start` with `clientUserMessageId`; correlation does not prove deduplication |
| Steering | Live user input, with queued/merged prompt correlation | `turn/steer` with `expectedTurnId`; stale/no-active-turn is an error |
| Cancellation | `interrupt` with `cancel_queued:true`, negotiated receipt, interrupted result and child accounting | `turn/interrupt`, then terminal interrupted `turn/completed` and child accounting |
| Pending requests | `can_use_tool`, question callbacks, cancelled requests and pending requests in initialize response | Command/file/permission approvals and MCP tool-call approvals (`mcpServer/elicitation/request`); questions through FF's `ff_questions` tool, because the pinned native `request_user_input` is usable only in Plan mode; live-thread pending-request replay |

Claude launch also explicitly selects model and permission mode, enables partial output and replay-user-message receipts, and keeps native persistence enabled. The 2.1.317 `--permission-mode` choices are `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk` and `plan`. `manual` is the CLI name for default and `system/init` reports it as `default` (probe C2), so profiles store the CLI name and the adapter compares init values through recorded probe evidence. Probe C4 showed that `can_use_tool` arrives through `--permission-prompt-tool stdio` without `--permission-prompts host`. The probes ran 2.1.317 with dummy API-key contexts, so they prove the protocol and not subscription auth.

Claude `--bare` and simple mode skip subscription auth and cannot be used. `--safe-mode` preserves auth but disables MCP; it is not a proven combination with the required FF reporter. The recipe uses a dedicated context, `--setting-sources user`, host-owned settings, strict explicit MCP configuration and controlled discovery of hooks/plugins/skills. Preserve intended repository instructions without importing Paseo integrations. With user-only setting sources, 2.1.317 loads the workspace `CLAUDE.md` only from an `--add-dir` directory and only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`, so the launch passes exactly the worktree as its one `--add-dir` and sets that variable. In probe C7 this loaded the instructions while the planted project hook and project MCP server stayed inactive. Managed policy still applies. Prove isolation, subscription auth and reporting together before shipping; fail if policy prevents the combination.

For Codex, use a dedicated `CODEX_HOME`, explicit effective model/sandbox/approval settings, and disable unselected integrations through version-valid configuration. Every launch sets `features.plugins=false` and `features.apps=false`; without them 0.162.1 contacted github.com and chatgpt.com (probe X12). Treat the execution project as untrusted for project config/hooks/rules; preserve task/repository instructions intentionally. User/system/cloud configuration may still contribute settings, so verify effective capabilities. An empty MCP map is not proof that merged settings were erased. Do not use external `chatgptAuthTokens`, token-refresh callbacks or cloud/remote services.

On the pin, `thread/start` with `cwd` records the project as trusted in the context's `config.toml` and reloads project configuration. That is how a planted project MCP server was started in probe X4b (pinned `thread_processor.rs`); without trust, project layers load disabled. The worker therefore runs with its process working directory set to the canonical worktree, and `thread/start`, `thread/resume` and `turn/start` never carry `cwd`. Before every `thread/start` and `thread/resume`, FF reads `config/read` for the worktree with its layers and refuses unavailable, unknown or inconsistent layers, an enabled project layer, recorded project trust, and any MCP server other than FF's own. Until probes show that disabled project layers stay inert for new and resumed threads, any reported project layer is refused. FF does not replace the reported layers with a filesystem existence check. A startup-status tripwire for unexpected servers detects a failure only after it happens and never counts as prevention.

Both adapters use the existing session-scoped FF reporting MCP through a private configuration outside the worktree. The native process receives only that scoped reporting credential, never the host enrollment credential. Required reporting initialization failure blocks the first prompt. Native MCP connectivity, authorization and report deduplication remain independently checked. No plain-text report scraping substitutes for the reporting contract. FF sets no tool-approval override for its own MCP servers and never changes the owner's selected policy to let them run. Under that policy Codex may first ask the user to approve a reporting call (probe X11 raised `mcpServer/elicitation/request` with approval kind `mcp_tool_call`), and FF presents it as an ordinary native approval. If a selected native policy cannot run required reporting or questions without alteration, the host publishes that profile as unavailable (`invalid_config`, with the protected reason `required_capability_blocked`). Probes record each pinned policy's outcome. An outcome a synthetic probe cannot attribute to the policy itself, such as Claude `auto` mode's classifier refusing a reporting call it could not evaluate (probe C13), is recorded as unproven: the profile stays unavailable with `required_capability_unproven`, never ready and never permanently blocked, and bounded authenticated UAT remains a separate later check.

## Permissions, questions and task behavior

Require the owner to select the native policy explicitly; missing permission, sandbox or network settings make a standalone profile incomplete. Do not silently broaden or restrict it at setup, Start or resume. Preserve existing Paseo-selected modes. Setup may suggest Claude `manual` (the CLI name for default) or Codex `on-request` with `workspace-write` and human approval review, with no preselected value: Claude's ordinary mode can pause for edits/commands; Codex can permit writes within its selected workspace sandbox without asking. These are documented choices with different consequences, not equivalent policies or an all-actions approval promise. Managed restrictions win.

A worktree provides ownership and Git isolation, not an OS security boundary. This design adds no FF OS-sandbox requirement; actual containment, if any, comes from the selected native policy. Claude safe-mode controls customization, not filesystem isolation. Native model access and FF reporting require their network connections; command/tool network access follows the explicitly selected native policy. Reject an incompatible effective policy instead of modifying it behind the owner's back.

Represent each pending request by FF session, backend, worker generation, native request ID and exact request fingerprint. Keep every outstanding request, including subagent requests; the current single-attention projection must not hide others. The server rechecks current role, session ownership, offered actions and request freshness when an answer is submitted. Expired/replaced requests and old worker generations are rejected. Browser disconnects do not approve, deny or answer automatically.

Translate only native offered responses and scopes. Preserve deny versus cancel, allow-once versus session grants, and requested filesystem/network subsets. Each offered action carries an explicit allow or deny behavior derived from the native decision, and the server validates both the offered action ID and that behavior before any write. Codex `decline` denies and lets the turn continue; `cancel` denies and interrupts the turn. A decision the native would accept but did not offer is refused (probe X6). Legacy Paseo actions without a behavior keep today's classification. Browser payloads cannot inject arbitrary tool inputs or persistent permission rules. Durable response dispatch is separate from native consumption: a pipe write or a `serverRequest/resolved` event alone does not prove an approval took effect. Ambiguous delivery remains reconciling.

Use stable question identities with selected-option arrays and separate custom text. Adapt native schemas at the boundary; do not join/split on commas or use display headers as global IDs. Cover duplicate headers, multiple questions, empty selections where valid, custom answers and cancellation. Both adapters must validate native timeout/auto-resolution behavior so FF never invents a user answer.

On the 0.162.1 pin, Codex's native `request_user_input` is usable only in Plan mode or behind an under-development feature. Default mode advertises it with a Plan-only description, but a valid call gets an explicit tool result rejecting it as unavailable outside Plan mode, and no `item/tool/requestUserInput` reaches the client. The tool also requires two or three options per question and gives the model no way to set `isSecret` (probe X7). FF switches no mode and enables no unsupported feature. Codex questions use `ff_questions.ask` instead: a session-scoped FF MCP tool that the supervisor serves on loopback beside the reporting server. The supervisor holds each call until a user answers or declines, or until FF withdraws it; a declined or withdrawn call never carries an answer. Interrupting a turn does not close a held call on the pin (probe X14c), so FF withdraws that turn's held questions when it observes the matching interrupted terminal, and a later answer is refused. The tool's `secret` field is FF's marker, not a native flag. Each call passes the owner's normal native tool approval first, so a user may see a permission request and then the question. X7 stays a recorded native limit, not native support, and Codex questions count as supported only after the question-tool probes pass.

Automatic host-only answering applies to a question's secret marker. For Codex that marker is the `secret` field of FF's question tool, which the model sets when it asks; native `isSecret` cannot be produced on the pin. Claude's native question schema has no equivalent flag; do not claim automatic secret classification. For flagged requests, the browser shows a host-only instruction and cancel, never a value field; the server rejects browser answer POSTs against the sanitized current-request marker. If one question is flagged, route the whole response locally. Ordinary web answers retain the existing server command path and storage.

Offer "Answer on execution host" for any current question, including Claude questions. A masked `runner answer --local` command uses private supervisor IPC, authenticates the execution owner's OS identity and exact connector instance, and answers the exact current request. This is a local-operator workflow, not a browser-forged web actor or a new native secret flag. The browser action provides instructions without collecting the value. Serialize local and web responses against the same current-request identity so a race cannot answer twice. No encrypted server-secret platform or new retention store is introduced.

In FF's host-local answer channel, keep answer bytes volatile, off argv/environment/history, logs, event spool and command ledger, and send them only through protected live IPC/native pipes. Persist a fresh local response-command ID, request fingerprint, destination, generation, operation and dispatch barrier, excluding the answer value and every raw/salted answer hash. This local no-replay contract differs from the server full-payload digest contract: any seen local ID returns its recorded state and never redispatches, regardless of a newly supplied value. Before dispatch, lost volatile input requires local reentry with a fresh ID only after proving the same request is still pending and the old ID never crossed its barrier. After a barrier, unknown consumption stays reconciling; do not solicit a replacement ID as a replay workaround. Lost-generation requests expire. These rules preserve durable dispatch evidence without durable local-answer payloads.

Proposed privacy boundary: the native tool receives an answer as conversation/tool input and may persist it or disclose it to its selected model under native semantics. The masked host-local UI must explain this before accepting input. Codex's pinned handler demonstrates this behavior, and an answer delivered through FF's question tool reaches the model as tool output under the same limits. For flagged or locally answered requests, FF excludes explicit response fields from server commands, events, audit and history projections, and redacts known exact live answer values before its spool when available. FF cannot detect a secret typed into an ordinary web answer or comment. This is not general DLP or a guarantee against model echoes, transformed text or derived content after a restart. Do not promise native non-persistence or patch the native tool. Native authentication stays entirely separate: this question channel must never import login credentials, sessions or tokens.

Stream output and tool progress from actual events with stable event identity. Preserve bounded history backfill, source cursors, plan/progress data where supplied, token usage and errors. Unknown usage is unavailable, not zero; provider cost estimates are labeled estimates and never equated with subscription charges. Native result/turn completion alone does not mark a task Done. Human acceptance remains required.

Summaries are explicit, idempotent commands over a frozen source-session cursor. No summary worker runs when summaries are disabled or unconfigured. Summary execution uses the frozen backend and configured summary profile; failures do not move to another model. Reports/artifacts retain run/session attribution, path/symlink protections, sensitive-file exclusions and bounded reads. Git receipts record observed state, not a model's claim.

Wrap-up requires all sessions and owned background work to be settled, no unresolved commands or approvals, clean tracked/untracked state, and commits pushed to the expected upstream. Missing upstream, unknown descendants, ownership mismatch or incomplete evidence blocks cleanup. Recheck immediately before archive; never force-remove the worktree. Keep archived receipts readable after the native process/workspace is gone. Native background shells can outlive a turn, so an idle UI event is insufficient.

## New supervisor and durable recovery

The proposed supervisor is a new FF host-local process, separate from the HTTP polling connector. A single connector instance/supervisor serves both standalone backends through its enabled profile set, with one native worker per FF session. It owns native stdin/stdout for each worker's lifetime, private IPC, durable event spool, process identity and exclusive session ownership. Backend identity remains per session; no cross-backend native-ID lookup is permitted. The connector can reconnect without closing native pipes.

### Intentional stop versus loss of connection

Normal SIGINT/SIGTERM/Ctrl+C of the foreground runner requests cancellation and quiescence of only its own standalone supervisor/workers, records observed outcomes and preserves journals/worktrees. Close native workers and the supervisor after confirmed quiescence; normal shutdown must not silently leave background work. A stop timeout or unknown descendant reports uncertainty and a non-success exit, with enough owned identity retained for a later stop/recovery attempt. Per-run cancellation remains available.

Provide `runner status`/`runner list` and `runner stop`, scoped to the saved connector instance and all of its owned standalone workers across both backends. Never enumerate answer payloads or kill unrelated native CLI sessions, another connector's workers, or Paseo daemon/resources. This standalone lifecycle does not change existing Paseo resource ownership. There is no user-facing detach mode or automatic boot service in day one.

A connector crash or network disconnect is different: the supervisor survives, keeps native pipes open and retains already-admitted work for durable reconnect. It admits no new prompts or effectful approval/answer commands while disconnected; local stop/cancel remains available. A separately owned process group/private IPC lets foreground signals reach the connector's shutdown handler without making connector death close worker pipes. This internal process separation is not an opt-in detach feature. If the host kills the whole process tree, use the supervisor/worker-crash rules; if the shutdown request never reaches the supervisor, report a crash/uncertain stop rather than claiming intentional cancellation.

### Capacity and account limits

The execution host owner configures the active-session cap locally per standalone backend, initially one Claude session and one Codex session. Publish limits and current capacity read-only in sanitized catalog/status; add no DB-admin write or dashboard setting. Changes affect future admission and never kill active work when a cap is reduced. Primary and summary sessions share their backend's slots. Waiting for human input and owned native background work count as active; release a slot only after settlement is observed. A retained idle process consumes no inference slot, and the existing same-task active-run reservation remains unchanged. Unknown activity after failure holds its slot until reconciled.

Reuse the existing durable queue, command identities and fencing for FIFO admission of eligible launches within each backend, with a stable tie-break for equal queue times. A launch/prompt/summary waiting for capacity remains queued without native effects and has no automatic expiry/TTL, matching offline-queue behavior. A pending human request may hold its slot until answered or explicitly cancelled. Show the authorized user's own queued time and capacity reason, not an exact global position that exposes other projects.

Cancel-before-launch remains available through current `run.cancel` RBAC. Atomically remove the launch from admission eligibility before native Start; a race with dispatch uses the durable actual evidence and must not falsely claim that no work started. Controls for active sessions bypass capacity-waiting launches so a capacity wait cannot block later control delivery. Keep capacity-waiting launches pending rather than claimed-and-held, so lease expiry does not repeatedly redeliver them. Capacity waits hold no DB connection and do not block heartbeats. Slot reservation/release belongs to the owning supervisor with durable recovery. This adds no scheduler service, priority system or fairness platform; the cap does not control personal CLI sessions, account use outside FF or native child concurrency within a session.

When a quota/account limit occurs mid-run, project the actual native waiting or terminal evidence. Preserve the exact session/worktree and report the limit safely. After recovery, require explicit authorized continuation; never retry automatically at the reset time, switch model/backend/auth, or replay a prompt to free/recreate a slot.

### Dispatch evidence and recovery

Local IPC must be restricted to the execution owner and exact connector instance. Persist backend, native session identity, supervisor/worker generation, boot/process-start identity, workspace ownership and immutable command digest. A PID alone is not identity. Hold an OS-backed exclusive owner lock; a server lease expiry must not create a second writer.

For each ordinary server-command side effect, fsync the accepted command record, then fsync a dispatch barrier before writing once to the native transport. Persist native receipts/events before acknowledging them to the connector. A duplicate server command ID with the same payload digest returns its recorded state; a different digest is rejected. After restart, no barrier means first dispatch remains possible; a barrier without evidence means delivery is uncertain and must not be repeated. Host-local answers instead use the metadata-only, no-replay rule above and never store an answer digest.

This provides at-most-once FF dispatch under intact durable storage and exclusive ownership. It does not provide exactly-once native model/tool execution. The price is an explicit reconciling state when the process dies between the barrier and the receipt. Native IDs and JSON-RPC request IDs are correlation, not a durable deduplication contract.

| Failure | Required outcome |
| --- | --- |
| Connector crashes/reconnects or network drops, supervisor survives | Reconnect to the same supervisor; replay durable FF events from the last accepted cursor; keep live questions and admitted work; accept no new effectful admissions offline and do not resend native commands. Intentional shutdown follows its separate cancel/quiescence contract. |
| Supervisor crashes | Fence all new delivery. Original pipes are not assumed reattachable. Identify and quiesce the old owned worker/descendants before restoring anything. A surviving orphan or uncertain command remains reconciling; never create a competing worker. |
| Native worker crashes | Preserve events/history; expire that generation's pending requests; reconcile positive receipt/terminal evidence. Any continuation is explicit and opens the exact recorded session after quiescence/config checks. No automatic prompt replay. |
| Host reboots | Invalidate old process identities by boot ID; recover the FF journal and native history. A previously dispatched command without proof remains uncertain even though its PID is gone. No automatic re-enrollment, fork or replacement run. |

Disable automatic interrupted-turn continuation for Claude (`CLAUDE_CODE_RESUME_INTERRUPTED_TURN=0`). Prove Codex resume does not implicitly restart unfinished work under the chosen settings. Resume is allowed only after exact identity/config checks and cannot itself become an unrecorded model command. Partial history, a stale status, an expired lease or a missing message is not proof of non-delivery.

Codex's pending callbacks are in memory; its live-thread resume path replays them, but worker death loses them. Claude exposes pending requests on initialization at recent versions, also without a demonstrated durable callback guarantee. FF's live supervisor is therefore the primary reconnect path. New generations never receive old native approval IDs.

Disk-full/fsync failure stops new admission. Preserve corruption for repair; reuse the journal's bounded torn-final-record handling. Backpressure must not discard terminal events or approvals. Descendant containment and cancellation need platform-specific proof; unaccounted detached work blocks wrap-up instead of being reported cancelled. Offline hosts retain last known evidence with offline/reconciling status, not manufactured completion.

## Data compatibility and migration

Propose forward-only creation of two new, initially unused side tables: `collab_run_execution` for immutable run selection, and `collab_session_execution` for session/backend ownership and native binding. New primary keys reference existing FF run/session IDs logically; validate parent organization/project/run ownership in the same transaction. This conservative additive choice preserves existing local collaboration schemas, history and source/user state without ALTER, backfill or new constraints/indexes on existing tables. It does not depend on asserting that collaboration tables are deployed in production. No deployment, production inspection or mandatory two-phase cutover is part of this task. Any later migration execution in this work is limited to isolated test resources and new, unused schema; future deployment/integration requires separate authorization.

Run ownership records contain schema version, backend, host, frozen profile/configuration revision and capability snapshot. Session records contain the owning run/backend, opaque native session/thread identity and binding generation. Local paths, auth files and supervisor IPC credentials remain private on the host. New native IDs never enter `paseo_agent_id` and are not looked up across backends.

Retain explicit protocol/capability validation for versioned local records, journals and cached hosts. New Start selection, primary session and ownership rows are one transaction. The control plane must never queue or deliver native-backend commands to a host that has not advertised the exact supported backend/profile/capabilities. Existing old binaries do not gain new rejection logic by declaration; their catalog keeps new commands ineligible. Updated validators must explicitly preserve the new fields instead of silently stripping them. Cached offline catalogs and later withdrawals follow the selection rules above.

Existing validated v1 run/session commands and journal records remain legacy Paseo. Preserve native bindings and the existing recovery algorithm verbatim; no conversion, replay, fallback or migration of their native agents. An absent field is legacy only within the validated old format, never a guess for unknown/incomplete new records. Unknown ownership fails closed. Further sessions/summaries on old runs remain Paseo-bound even if future defaults change.

With Paseo disabled, old history and archived evidence remain readable. Controls that need its live integration show unavailable; enabling it reconnects only the original recorded host/instance/resource after identity checks. Installing the integration or changing a default does not reissue a prompt. Rollback may disable new Starts, but readers for recorded new-backend runs must remain available; rolling back must not reinterpret them as Paseo.

## UI and safe public errors

Execution setup shows the host's complete advertised profile set grouped by backend, sanitized auth readiness and capabilities. It distinguishes tool installation, native sign-in and FF host enrollment without revealing internal paths or tokens. Settings edits keep existing project-admin/internal-read gates. Task/project defaults select an eligible profile at Start without changing the host's enabled set. Start shows the selected backend/model/policy; capacity is read-only host-owned status. Existing task commands retain their current RBAC checks.

Task execution shows actual queued, running, waiting, offline, interrupted, failed and reconciling states, including the user's own queued time and capacity reason. It displays all pending requests and exact response scope. Flagged secret requests offer host-only instructions and cancel with no value field; ordinary questions also offer "Answer on execution host" while retaining web answering. Output, usage availability, artifacts and explicit summary/wrap-up results remain visible. Unknown outcome remains recoverable. A lost response cannot present a successful operation merely because the button was clicked.

Proposed changed/new public messages and triggers:

| Message | Trigger |
| --- | --- |
| Choose a complete execution profile before starting. | Engine, model or explicit native permission/sandbox/network policy is missing. |
| This execution profile is unavailable. Contact the execution host owner. | Missing tool/integration, incompatible version or invalid effective configuration, including a selected native policy that cannot run required reporting or questions. |

## Acceptance before release

These are behavior groups for a later test-first implementation plan, not an implementation sequence. For each changed contract, first write a deterministic failing regression/acceptance test and observe the intended failure, then implement and refactor with passing tests. Keep deterministic native-protocol probes early enough to expose an unsuitable interface before substantial adapter work.

Authenticated real-tool UAT for both backends is a completion/release gate; fixture-only evidence is insufficient. The owner performs native login in each dedicated context. After deterministic implementation/checks and a reviewable disposable test setup are concrete, request separate bounded prompt authorization describing accounts, repository, host, scenarios and quota limits. Do not ask for accounts/budget now or treat design approval as permission to authenticate or consume quota. Complete authorized preparation first; no source/user resources are modified for UAT. Until the owner authorizes and those scenarios pass, native-support completion and release remain blocked.

| Scenario | Expected result |
| --- | --- |
| Fresh standalone setup with Paseo absent | One connector/supervisor advertises both native profile sets with exact sanitized readiness; at least one complete profile permits startup; no automatic engine/model/policy or Paseo discovery; project default selection does not hide other profiles. |
| Explicit Start through dashboard for each backend | One task-linked run/worktree/session; frozen profile; reporting ready before first prompt; real output, artifacts and usage availability; no API-key requirement. |
| Catalog selection and offline Start | Exact mapping/catalog/profile/backend/capability match is required; cached offline eligibility queues safely; missing or newly withdrawn selection fails with a settings instruction; no fabricated snapshot or changed backend at delivery. |
| Auth/config/limit failure | Safe actionable state; no token copying, implicit logout, API billing, alternative model/harness or integration fallback. |
| Permissions and questions | Selected native policy is preserved without silent broadening/restriction, and a policy that cannot run required reporting or questions is published unavailable and never altered; only offered actions are accepted, each with its explicit allow/deny behavior; native response scopes and ordinary multi-question/custom/comma/duplicate-header cases work; stale/revoked-role responses fail; no auto-answer on disconnect. |
| Flagged and locally answered questions | A browser answer POST to a flagged request is rejected; Codex flags come from FF's question tool, and Claude has no automatic secret flag. Any current question can be answered through the masked local-owner path without browser value collection; ordinary web answers retain their server path. Local answer values/hashes never persist, known live values are redacted, repeated IDs cannot redispatch and web/local races cannot double-answer. Warning explains native/model persistence and no DLP/model-echo guarantee. |
| Output, steering and cancellation | Ordered deduped history; prompt correlation survives merged inputs; stale steer cannot affect another turn; cancellation waits for evidence and accounts for background work. |
| Duplicate and lost commands | Same ID/digest cannot dispatch twice; changed digest fails; interrupt/approval receipt ambiguity stays explicit; partial history never authorizes replay. |
| Each of the four crash cases | Correct owner/generation recovered; no competing worker or automatic model continuation; complete positive evidence resolves outcomes, otherwise reconciling. |
| Intentional runner stop | Ctrl+C/SIGTERM cancels/quiesces only owned standalone work, preserves journals/worktrees and leaves no silently running workers; failed confirmation remains uncertain; scoped status/stop can inspect/recover it. |
| Capacity, queued cancel and quota exhaustion | Read-only published host-local limits govern primary/summary/waiting/background slots; reductions do not kill work; eligible launches are durable per-backend FIFO with no TTL. Controls bypass capacity waits; authorized queued cancellation prevents launch or reports the dispatch race honestly. Idle retention is free; quota continuation is explicit, never reset-time retry/fallback. |
| Corrupt/full journal and orphan child | New delivery stops; state remains available for repair; no false success or force cleanup. |
| Summary, reports and wrap-up | Explicit summary uses frozen backend/cursor; disabled summaries do no work; scoped reports dedupe; unsafe artifacts fail; dirty/unpushed/active/unknown work blocks archive; receipts remain readable. |
| Existing Paseo and old history | Original profile/journal bindings and recovery untouched; saved defaults do not imply opt-in; explicit enablement restores original integration access; disabled integration leaves history readable and controls unavailable; no conversion or re-enrollment. |
| Additive local data compatibility | Only forward-only new unused side tables are exercised in isolated tests; existing local schemas/history and source/user resources stay untouched; old unadvertised hosts never receive new-backend commands. No production check or deployment is implied. |
| Existing auth, Projects and polling | Current project `run.start`, explicit host mappings, role checks, one-time enrollment, command fences, Projects selection and bounded poll cadence remain intact; client-only membership grants no Start/filesystem rights. |

Both subscription backends and all required capabilities must pass before completion/release. If either native probe fails, hold the whole release; do not ship one backend, degraded questions or implicit API/Paseo fallback. Evaluate another supported native interface with evidence; return to the user only when a material capability/deployment change is unavoidable.

Unresolved engineering proof: Claude stdio control and config isolation together with the reporter under subscription auth (probes C1 to C12 passed with dummy API-key contexts); Codex questions through FF's question tool and the project-config gate for new and resumed threads; each pinned policy's effect on required reporting and questions; native receipt semantics, including the local no-replay answer channel; safe descendant accounting under supervisor/worker failure. These are release blockers, not permission to remove capabilities. Implementation follows the [implementation plan](2026-11-04-optional-paseo-implementation.md); authenticated native UAT still needs separate owner authorization.
